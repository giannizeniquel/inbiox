# Frontend cleanup (apps/web)

Objective: regain control of the frontend. Remove overengineering and dead code, put every file where `docs/arquitectura.md` § Frontend says, and add no new features.
Branch: one branch per phase in the worktree `/home/gianni/projects/inbiox-worktrees/front` (phase 0: `chore/limpieza-frontend-fase-0`, from `chore/limpieza-backend-fase-0` at `6fcefec`, so it carries the shared rules and glossary). Delivery: one PR per phase into the integration branch `test-refactor` (from `test` at `b543593`), after the backend PRs it builds on; `test` keeps the working app and receives no cleanup PR. Push, PR and merge are user decisions. Test runner: none runnable for Karma specs in WSL2; gates are listed in S3.

## Specs

- **S1 — Order first, no new features.** User: "Necesitamos recuperar el control, es una app muy vibecodeada." and "muy importante: sobreingenieria".
  - Every phase preserves behavior. Phase gate: S3 holds after the phase.
- **S2 — Phases** (plan agreed with the user and the backend session, L2–L3):
  0. Safety net: baseline of S3.
  1. Delete dead code (`FakeWhatsAppProvider` and the unused code listed in `07-frontend.md` § Código sin uso, each one verified before deletion).
  2. Move code to `data-access/<modulo>` + `features/<pantalla>`; rename folders only.
  3. Remove pass-through layers: use cases without their own logic and the `PROVIDER_INTERFACE` abstraction are absorbed into their module's store or service. Screen state does not go into `data-access` (rule 2 of `docs/arquitectura.md` § Frontend).
  4. Split giant components and services (`conversation.component`, `ticket.store`, `mercure.service`).
  5. Renames, in two parts (L29, L31):
     - 5a, now: folders, files, classes, types and selectors with the glossary (`docs/arquitectura.md` § Frontend rule 4, widened by the backend in `6ad4662`). Map and scripts: `odd/tasks/limpieza-frontend-fase-5/` (`map.json`, `moves.js`, `apply.js`).
     - 5b, with the joint API contract: JSON fields and the properties that mirror them, enum values on the wire, Mercure event types, role strings, `/api/...` routes and router URLs.
- **S3 — Safety net.** Gates after every phase, compared against the baseline below:
  - `ng build --configuration production` exits 0 with no new warnings.
  - `tsc -p tsconfig.spec.json --noEmit` reports no new errors (`ng build` excludes specs, so moving folders could break them silently).
  - Manual smoke: `docs/02_sistema-actual/09-guia-de-pruebas-manuales.md` (P-01..P-24) for the screens a phase touches.
- **S4 — Docs policy.** Each phase updates `docs/02_sistema-actual/07-frontend.md` in the same PR. `docs/arquitectura.md` is owned by the backend session; the frontend asks for changes instead of editing it.
- **S5 — Local environment.** The `web` container serves this checkout's sibling, and Mercure only accepts `http://localhost:4200`. To run the app from this worktree: `docker compose up -d --scale web=0` from the main checkout, then `ng serve --proxy-config proxy.conf.json` on port 4200 from `apps/web` here.

### Phase 3a plan (approved 2026-10-14, L13)

Scope: phase 3 of the frontend. A6 splits the services per the backend's module map (L13). Mapping in L12.

- **E1 — Errors keep their text.** No caller checks the use-case error classes (`instanceof` or `.name`); callers only read `err.message`. The classes go, and `extractApiError` moves with the logic so the backend's message still reaches the screen.
- **A1 — Pass-through use cases are absorbed into their module's API service**, with their small extras unchanged (trim, payload defaults, the `totalPages` calculation, the `extractApiError` wrap, the two "available" filters). Pages inject the service. No new store: the admin pages already hold their own state.
  - `administracion`: Create/Update/Deactivate/Reactivate/List for agents and users, `GetAvailableUsersForLinking`, `ManageAgentUserLinking`, and `CreateUser.loadAvailableAgents` go to `admin-api.service.ts`; the team and workspace use cases go to `team-api.service.ts` and `workspace-api.service.ts`.
  - `contacto`: `GetContacts`, `CreateContact`, `UpdateContact` go to `contacts-api.service.ts`, keeping their mapping to `UIContact` and their `err.message` handling (they never used `extractApiError`). The unused `filters` input of `GetContacts` is dropped.
  - `reporte`: `GetTicketParticipation` goes to `reports-api.service.ts`.
- **A2 — Use cases with their own logic stay:** `SendMessage`, `RetryMessage` (send/retry orchestration), `GetReportsDashboard` (13 calls with fallbacks), `ExportTicketsCsv` (download side effect), `BuildTimeFilterParams` (date maths, no API call). Renaming them is phase 5.
- **A3 — `PROVIDER_INTERFACE` goes.** One implementation, two methods used. `SendMessage`/`RetryMessage` inject `WhatsAppCloudProvider` directly; the manual providers in `app.config.ts` go (both classes are already `providedIn: 'root'`); the stub methods and the unused `uploadMedia`/`downloadMedia` go; the shared types (`Message`, `Ticket`, `DeliveryStatus`, …) stay in a model file of `data-access/conversacion/`.
- **A4 — Contacts screen state moves to `features/contactos/`:** `searchTerm`, `filters`, selection and `filteredContacts` go to a screen store there.
